# NecroCard — Product Brief

This is the input document for Kiro. Steering docs and specs are generated by Kiro from this brief, not written by
hand, so that `.kiro/` reflects real Kiro usage. Keep this file updated when scope changes.

## 1. One-liner

NecroCard is HyperCard in the browser, with an agent that builds a working stack from a plain-English description.

Tagline: **HyperCard, raised from the dead.**
Hackathon: Kiroween 2026, category Resurrection. Deadline Dec 4, 2026, 2:00 PM PT.

## 2. Who it is for and why it matters

- People who want to make a small interactive thing (a quiz, a choose-your-own-adventure, a flashcard deck, a tiny
  tool, an interactive zine) without learning a framework.
- Teachers and tinkerers who remember HyperCard and want the feeling back with modern sharing.
- Anyone curious what "describe it and it exists" looks like when the output is editable, inspectable software rather
  than a black box.

The pitch for judges: HyperCard was the original no-code tool. Its model (cards, objects, small scripts) is still the
most approachable way to describe interactive software. The missing piece in 1987 was an author that writes the first
draft for you. NecroCard adds that, and keeps every generated object and script editable.

## 3. Core model

- **Stack**: name, list of backgrounds, list of cards, stack script, metadata (created, modified, author).
- **Background**: shared objects and script for the cards that use it.
- **Card**: belongs to one background; own objects and script.
- **Objects**: `button`, `field`, `image`. Common properties: id, name, rect (x, y, w, h), visible, script.
  - button: style (`rect`, `roundRect`, `transparent`), label, autoHilite.
  - field: text, lockText (read-only), style (`rect`, `scrolling`, `transparent`).
  - image: src (data URL or asset id), 1-bit dithered on import.
- Object ids are stable; names are user-facing and used by scripts (`field "Name"`).
- The whole stack serializes to one JSON document. Round-trip must be lossless.

## 4. NecroTalk (frozen HyperTalk subset)

Freeze this list in the interpreter spec. Anything not listed is out of scope for the hackathon.

**Structure**
- `on <handler> [params] ... end <handler>` with system handlers `mouseUp`, `mouseDown`, `openCard`, `closeCard`,
  `openStack`, and custom handlers invoked by name: a statement `<name> [arg, arg...]` calls the handler `<name>`
  in the same script; if no such handler exists, it is a runtime error `Unknown command "<name>"`.
- Message passing order: object, card, background, stack.
- Comments start with `--`.

**Navigation**
- `go to card N`, `go to card "Name"`, `go next`, `go prev`, `go first`, `go last`.
- `visual effect dissolve | wipe left | wipe right | scroll up` applied to the next `go`.

**Data and properties**
- `put <expr> into <container>` where container is `field "Name"`, a local variable, or `it`.
- `put <expr> before | after <container>`.
- `get <expr>` sets `it`.
- `set [the] <property> of <object> to <expr>`; readable properties also via `the <property> of <object>`.
- Object references: `button <expr>`, `field <expr>`, `image <expr>`, `card <expr>`, and `me`. The name is any
  expression, usually a string literal, so `button x` with a variable `x` is valid. `background` and `stack`
  references, and references with no name other than `me`, are parse errors in this version.
- `me` is the object whose script is currently running. When a message passes up the chain, `me` becomes the card,
  background, or stack whose script handles it. The dispatcher supplies this to the evaluator.
- A field reference in expression position evaluates to the field's text: `put field "Score" + 1 into field "Score"`.
- A bare `the <name>` with no object is valid only for `the date` and `the time`; anything else is a runtime error
  `Unknown property "<name>"`.
- Reserved words (every keyword in the tokenizer) cannot be used as variable or handler names; the parser rejects
  them with `"<word>" is a reserved word`.
- `do` and `sort` are rejected at parse time with the exact messages from the steering examples, so Summon can
  catch them before a script is loaded.
- `global <var>` declares a stack-wide variable.
- `answer <expr> [with <btn1> [or <btn2> [or <btn3>]]]`, result in `it`. No `with` means one "OK" button. More than
  three buttons is a parse error, as in HyperCard.
- `ask <expr> [with <default>]`, result in `it`.

**Control flow**
- `if <expr> then <stmt>` and `if <expr> then ... [else ...] end if`. `else if <expr> then` chains share a single
  `end if`, as in HyperTalk; they parse to nested if statements.
- `repeat <N> times ... end repeat`, `repeat with <var> = <a> to <b> ... end repeat`, `repeat while <expr>`.
- `exit <handler>`, `next repeat`, `exit repeat`.
- `pass <handler>`: hand the message on to the next object in the message path (object, card, background, stack).

**Visibility and feedback**
- `show <object>`, `hide <object>`, `beep`.

**Expressions**
- Numbers, strings in double quotes, variables, `true`/`false`.
- Arithmetic `+ - * / mod ^`, unary minus, concatenation `&` and `&&` (with space).
- Grouping parentheses `( <expr> )` anywhere an expression is allowed, including computed object names such as
  `field ("Q" & n)`. An object name binds tightly, so `field "Score" + 1` means `(field "Score") + 1`.
- Comparison `= <> < > <= >=`, also `is`, `is not`, `contains`.
- Logic `and`, `or`, `not`.
- Functions: `the number of cards`, `the number of words | lines | chars of <expr>`, `the date`, `the time`,
  `random(N)`, `length(<expr>)`, `word N of <expr>`, `line N of <expr>`, `char N of <expr>`. Chunks may nest for
  reading (`char 1 of word 2 of x`); this fell out of the parser design at no cost and is allowed.
- Any `<name>(<args>)` parses as a function call; calling a function that does not exist is a runtime error
  `Unknown function "<name>"` with the line number. Built-in functions check their argument count:
  `random` and `length` take exactly one argument, otherwise `Line N: random expects 1 argument`.
- Calling a handler by name is limited to 200 nested calls; deeper recursion is a runtime error. Inside a handler
  that was called directly (not via a message), `pass` simply ends that handler.

**Phase 2 (only after the core above is implemented, tested, and Summon works end to end)**

These are small enough to add in week 3 or 4 and each adds real value. The interpreter design must not block them,
but no spec task for them is created until the core is done. Order of value:

1. `item N of <expr>` chunk with comma delimiter (read-only). Enables simple lists in fields. Also `the number of items of`.
2. `find "text"`: jump to the first card after the current one whose fields contain the text, highlight the field.
   No `find whole`, no `find in field`.
3. `play <notes>`: one synthesized voice via Web Audio, note names with optional octave and duration
   (`play "c e g c5h"`), `play stop`. One instrument. Makes sample stacks and the video more charming.
4. `send "<message>" to <object>`: dispatch a message to another object through the normal handler chain. The engine
   already dispatches messages, so this is a small addition. No `send ... to HyperCard` or to other stacks.

**Out of scope (do not add during the hackathon)**: paint commands, external commands (XCMD/XFCN), menus, `sort`,
`do` (it is eval and breaks ahead-of-time validation of generated scripts), chunk ranges (`word 2 to 4`),
chunks as put targets, number formatting.

## 5. Editor

- **Browse mode**: cards render at 512 x 342 logical pixels (original Mac resolution), scaled to fit. Clicking runs scripts.
- **Edit mode**: select, drag to move, drag handles to resize, double-click to open the object's script. Property
  inspector panel. Tools: button, field, image (import file). Card menu: new card, delete card, next, prev, card info.
- **Script editor**: syntax highlighting for NecroTalk, line numbers, errors shown inline with line numbers, "Explain"
  and "Fix" actions that call the agent.
- **Message box**: single-line NecroTalk input at the bottom, like the original, for trying commands live.
- Undo for move, resize, delete, and script edits (single linear history is enough).

## 6. Summon (AI authoring)

- Input: a paragraph describing a stack. Output: a stack JSON that validates against the schema, with scripts that
  parse under NecroTalk.
- Pipeline: prompt with the schema and the NecroTalk grammar, request JSON, validate, parse every script, retry once
  with the error list if anything fails, then load into the editor.
- Also: "Explain this script" and "Fix this script" from the script editor, which send the script plus the error.
- Served by a small serverless function with a hard daily request cap and per-IP limit, plus a bring-your-own-key
  option stored only in the browser. The demo URL must stay free through Jan 29, 2027.
- Ships with 3 to 4 sample stacks so the app works without any AI calls.

## 7. Persistence and sharing

- Autosave the open stack to localStorage.
- Export and import `.necrocard.json`.
- Share by URL: compressed stack in the fragment for small stacks; serverless blob store with a short id for larger ones.

## 8. Visual design

- 1-bit Macintosh System 6 look: black on white, dither patterns for fills, 1px bevelled buttons, a Chicago-like bitmap
  font for UI and a Geneva-like font for field text. No anti-aliasing on the card surface where the browser allows it
  (bitmap-style fonts at their native pixel size; full font AA control is not possible cross-platform).
- **Fonts must be open-licensed lookalikes** (OFL, CC, or similar) with the license file committed next to them.
  Apple's Chicago, Geneva, and Monaco are proprietary and the hackathon rules forbid unlicensed third-party material.
  Never use those names in the UI, README, or video; say "classic Mac-style bitmap fonts".
- Transitions: dissolve, wipe, scroll. Cards are DOM, so transitions are implemented as **stepped** effects over the
  DOM card: wipe and scroll via `clip-path` or `transform` in discrete steps, dissolve via an animated 1-bit dither
  `mask-image` sequence. No smooth opacity fades or eased CSS animations. A canvas overlay is allowed only if it does
  not require rasterizing the DOM card. Duration 333 ms, roughly 10 to 12 discrete frames.
- The chrome around the card (menus, inspector) may use the same style or a quiet dark theme; the card itself is sacred.
- Spooky but tasteful: the sample stacks carry the Halloween theme; the tool itself stays faithful to HyperCard.

## 9. Technical choices

- TypeScript, Vite, no UI framework. DOM rendering for cards and objects. CSS for the 1-bit look.
- Interpreter: hand-written tokenizer, recursive-descent parser to an AST, tree-walking evaluator. No eval.
- Tests: Vitest for unit tests, fast-check for property-based tests, Playwright for end-to-end.
- Hosting: static site on Cloudflare Pages or GitHub Pages; one Cloudflare Worker (or equivalent) for Summon and share blobs.
- Node 22+. Single `npm run dev`, `npm test`, `npm run build`, `npm run e2e`.

## 10. Non-goals

- Importing real HyperCard `.stack` files.
- Full HyperTalk compatibility.
- Paint tools, sound, printing, multi-user editing, accounts.
- Mobile editing (mobile browse mode is nice to have, not required).

## 12. Spec plan (in order)

1. `stack-model`: types, JSON schema, serialization round-trip, sample stacks.
2. `necrotalk-interpreter`: tokenizer, parser, AST, evaluator, message passing, error reporting. PBT on parser
   round-trip and evaluator invariants.
3. `browse-mode`: rendering, hit testing, running handlers, navigation, visual effects.
4. `edit-mode`: selection, move, resize, inspector, tools, undo.
5. `script-editor`: highlighting, inline errors, message box.
6. `summon`: prompt, schema validation, retry, serverless function, caps, BYO key.
7. `sharing`: localStorage autosave, export/import, URL share, blob store.
8. `retro-skin`: 1-bit styling, fonts, patterns, transitions.
9. `necrotalk-phase2` (only if specs 1 to 7 are done by Nov 23): `item` chunks, `find`, one-voice `play`, `send`.

## 13. Kiro plan (what to use and why)

- **Steering** (always): `product.md` (HyperCard fidelity rules, what NecroTalk is and is not), `tech.md` (stack, no
  framework, no eval, test tools), `structure.md` (folders, naming). Conditional: `necrotalk.md` on `src/interp/**`
  (grammar rules, error message style), `retro-ui.md` on `src/ui/**` and `**/*.css` (1-bit rules).
- **Specs**: the eight above, each with requirements, design, tasks, executed through Kiro.
- **Hooks**: run Vitest on save for `src/**`; type-check and lint before the agent finishes a task; regenerate sample
  stack fixtures when the schema spec changes; run Playwright smoke after UI tasks.
- **PBT**: enable on interpreter requirements (parse then print then parse is stable; `put` then read returns the same
  value; navigation never leaves the valid card range; serialization round-trip is identity).
- **MCP**: Playwright MCP to drive the editor and take screenshots during UI work. GitHub MCP for issues if useful.
- **Custom agents**: `necrotalk-reviewer` (checks grammar changes against this brief, read-only), `retro-design-reviewer`
  (checks CSS against the 1-bit rules, screenshots via Playwright MCP).
- **Surfaces**: CLI for specs, hooks, and batch tasks; IDE for the spec UI and diff review; Crew for parallel work on
  the interpreter and the editor once both specs exist. Record differences in `KIRO_USAGE.md`.
- **Powers**: install any relevant bundled powers (testing, deployment) and note what they contributed.
